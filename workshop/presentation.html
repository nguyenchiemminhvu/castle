01 / The problem space

Embedded systems pay for hidden decisions.

Many C++ features are useful on a desktop, but an embedded product has a much smaller budget and stricter timing.

01 / Memory

HEAP

The memory left depends on what ran earlier. Allocation can fail, and fragmentation makes memory hard to use.

02 / Control

EXCEPTIONS

Control can jump across several stack frames, which is hard to see at the call site.

03 / Dispatch

VIRTUAL

Virtual interfaces add runtime indirection and make the call target less visible.

04 / Dependencies

STL

Library facilities may rely on assumptions, headers, or runtime support that a target does not fit.

05 / Timing

UNKNOWN

Any operation with unclear worst-case work makes timing analysis harder.

These tools are not "bad practices", but unsuitable for embedded work.
Before we adopt a feature, we ask: how much memory, how can it fail, and how much work can it do?

02 / Storage by design

Make the memory budget visible.

The capacity is part of the type. The container owns its storage inside the object and does not silently grow.

03 / Failure as data

Make failure an ordinary result.

A full buffer or an empty queue is a normal condition that the system must handle every day. CASTLE returns a status for the caller to check.

Typical container operationRead / write
status::ok

Continue with the accepted data.

status::full

Reject the item, apply backpressure, or record a diagnostic.

status::empty

Handle “nothing to read” as an expected state.

Expected runtime outcomes use status or bool. Programmer-contract violations use the configured assertion policy.

04 / Abstraction with a budget

Pay for abstraction deliberately.

The goal is not to remove abstraction. It is to choose where work happens and make storage and dispatch costs inspectable.

01 / DEFAULT PATH

Templates and static dispatch

Types and behavior are selected at compile time. The compiler can specialize the code without a runtime base-class lookup.

02 / OWNED CALLABLES

In-place storage

The function wrapper keeps a callable in a bounded local buffer. A callable that does not fit is rejected at compile time.

03 / EXPLICIT SEAMS

Limited virtual interfaces

Core data structures avoid virtual dispatch. Observer, visitor, and delegate interfaces use it, so explain its cost and why it helps.

The same discipline applies to language and library features: no exceptions or RTTI, and no required STL containers or algorithms.

06 / The daily coding shift

A different everyday coding habit.

The code has a few more explicit lines. Those lines are not noise. They record decisions the system already had to make.

event dispatchCASTLE STYLE
struct TickEvent {};

using dispatcher_type = castle::events::event_dispatcher<
  castle::events::event_tag_config<TickEvent, 4U, void(uint32_t)>>;

dispatcher_type dispatcher;
auto sub = dispatcher.register_callback<TickEvent>([](uint32_t){});
dispatcher.dispatch_event<TickEvent>(1U);
sub.unsubscribe();

07 / Review mindset

A code review asks different questions.

We still check correctness and tests, but we also ask four resource questions.

01

Memory

Where does the storage live, and who owns it? Is it borrowed or owned by the object? What is the maximum size?

02

Capacity and failure

What happens when the queue is full, the buffer is empty, or a lookup fails? Is it handled or ignored?

03

Timing and work

What work happens in the worst case? Is that cost right for the task period?

04

Concurrency and lifetime

Can this run from more than one task or an interrupt? Who protects shared state? Can a callback outlive its object?

A strong review explains these answers from the design and code, not only from a passing test.

08 / Impact and limits

Predictability improves. It still must be proven.

CASTLE makes component behavior easier to reason about. It does not replace evidence at the system level.

What becomes easier

Clearer engineering budgets

  • Known storage bounds help with RAM budgeting.
  • Explicit statuses help define recovery behavior.
  • No heap, exceptions, RTTI, or STL means less runtime machinery to account for.
  • Consistent patterns make code easier to maintain across teams.

What still needs evidence

System-level validation

  • Measure worst-case timing on the actual microcontroller.
  • Size buffers using real traffic and fault scenarios.
  • Understand the OS backend, scheduler, and interrupt constraints.
  • Check synchronization, compiler, and processor behavior.
BOUNDED COMPONENTS + EXPLICIT POLICY + TARGET VALIDATION = MORE PREDICTABLE SYSTEMS

09 / Take it into the next change

Design the bounds.
Then write the code.

When we review a component, we should explain how much memory it can own, what happens at its limit, and what work it can do.

01 Choose storage and capacity up front.

02 Make expected outcomes explicit.

03 Keep lifetimes and dispatch visible.

04 Measure timing and concurrency on the real target.

Fewer hidden decisions. More deliberate systems.
