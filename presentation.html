01 · Motivation

Make the important costs explicit.

Embedded software does not lack C++ features. What it lacks is "invisible" budgets.

0
mandatory heap allocation
0
exception-driven error path
0
RTTI requirement
N
compile-time capacity / bound

Instead of “it probably fits”

vector<T, N>, ring_buffer<T, N>, fixed strings, fixed registries and inline callable storage expose the budget in the type.

Instead of “something threw”

castle::status makes normal bounded failures visible: ok, full, empty, not_found, invalid_config.

Why this matters for automotive / firmware work

Deterministic behaviors make memory, capacity, failure paths, and timing assumptions easier to review, test, and integrate into a project’s own safety process.
Reducing the hidden cost behind dynamic memory allocation and handling exceptions can improve the performance and stability.

The runtime contract is deliberately small.2 / 9

03 · Bounded data

Put memory shape and failure on the API.

The same model repeats across storage, containers, and text/serialization. For example:

Fixed-capacity sequence

castle::container::vector<T, N> stores up to N live elements in the object; append returns castle::status::ok or full.

Deterministic FIFO

ring_buffer<T, N> gives O(1) push/pop and makes overflow policy explicit via push() vs force_push().

Inline object lifetime

memory::construct_at, destroy_at, aligned storage, and SOO buffers support caller-owned memory without a general-purpose allocator.

A familiar API with a bounded contract
castle::container::vector<uint16_t, 8U> samples;

auto s1 = samples.push_back(1024U);
auto s2 = samples.push_back(2048U);

if (s1 == castle::status::ok) {
    // capacity is part of the type — not a surprise
}

if (samples.full()) {
    // choose the failure policy explicitly
}

Review-friendly behavior

There is no growth event hidden inside push_back(), and no exception is required to represent a normal capacity boundary.

Determinism starts with visible resource bounds.4 / 9
04 · Callbacks

Stateful callbacks without a heap-backed std::function.

Castle’s owning callbacks::function uses caller-selected inline storage and compile-time size/alignment checks.

Inline storage

Callable bytes live inside the function object. A lambda larger than the configured buffer fails at compile time.

No RTTI-based type erasure

Invocation, copy, move, and destruction are routed through stored function pointers over the inline object.

Then build registries on top

function_registry<Max, void(Args...)> keeps multiple callbacks in fixed slots and invokes them in slot order.

Fixed storage + explicit registration
castle::callbacks::function_registry<4U, void(int)> registry;
int total = 0;

auto sub = registry.subscribe(
    [&total](int value) noexcept {
        total += value;
    });

registry.invoke(2);
registry(2); // equivalent to invoke(2)

if (sub.valid()) {
    sub.unsubscribe();
}

Developer comfort

The programming model still feels like ordinary callback code: capture state, subscribe, invoke, unsubscribe. The key difference is that storage and capacity are explicit.

A small type-erasure mechanism, kept inside a deterministic budget.5 / 9

Event identity and callback signature are selected from the type system. Capacity is also visible at the same declaration point.

06 · Timing & scheduling

Turn callbacks into behavior: timers and exec policies.

The library separates “what to call” from “when to call it” — without requiring hidden threads or heap state.

tick_timer

Set a period, register fixed-capacity callbacks, then advance explicitly with on_tick(). Supports periodic, one-shot, and N-repeat modes.

exec_policy

Policies such as once, every_n, on_change, throttle, and periodic keep gating rules explicit and poll-driven.

Deterministic integration point

Timer callbacks run synchronously from the caller of on_tick(); policy callbacks execute in the caller’s thread. Threading is not smuggled in by the abstraction.

Example: periodic sensor publication
castle::events::tick_timer<4U> timer;

auto sub = timer.register_callback(
  []() noexcept {
    // sample + publish one bounded event
  });

timer.set_period(10U);
timer.start(
  castle::events::tick_timer_mode::periodic);

// from the scheduler / tick source:
timer.on_tick(1U);

A useful design pattern

driver → timer/policy → callback → event_dispatcher → fixed containers gives a readable path from hardware-facing timing to application logic.

Keep scheduling policy explicit; keep execution local.7 / 9
07 · Engineering view

What changes for the developer?

The goal is not “more templates”. The goal is making embedded constraints feel like normal API choices.

Before code review

Capacity, alignment, callback storage, and configuration are visible in types and template parameters.

During testing

Boundary conditions become ordinary test cases: full, empty, invalid configuration, expired subscription, repeated timer expiry...

During integration

Compiler abstraction, no-STL dependency, explicit status codes, and platform-aware low-level primitives keep integration surfaces small.

Portable by construction

Compiler variants cover GCC / Clang / ARM families in the supplied snapshot. The library centralizes portability macros rather than spreading toolchain conditionals through application code.

Predictable complexity

Many core operations document O(1) behavior or O(capacity) scans explicitly. Bounded storage removes reallocation as a hidden runtime event.

Process-compatible

CASTLE is designed with automotive safety requirements in mind, aiming to align with relevant standards and practices such as MISRA and AUTOSAR.

Library mechanisms support the safety process; they do not replace it.8 / 9
