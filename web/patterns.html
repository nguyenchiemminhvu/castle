Patterns

Allocation-free building blocks for observer notification, explicitly controlled singletons, visitor dispatch, decorated callables, guarded request chains, timed action sequences, and compile-time finite state machines.

#include "castle/patterns/{observer,singleton,visitor,decorator,chain_of_responsibility,action_sequence,fsm}.hpp"

Overview

The patterns module provides seven header-only building blocks for embedded code: observer notification, an explicitly managed singleton, variadic visitor dispatch, a chain of responsibility, a timed action sequence, a compile-time finite state machine, and a decorator for layered callable wrappers. None of them allocate on the heap or require RTTI or STL containers.

Observer and visitor dispatch through virtual functions. The FSM, the static chain, and the decorator use compile-time dispatch only, the bounded chain and action sequence store their callables in fixed inline slots, and the singleton is a plain static wrapper with no virtual calls.

Observer

Fixed-capacity observer interfaces and an observable registry for embedded event fan-out. Use it when a subject must notify a bounded set of listeners without dynamic allocation.

Dependencies

  • castle/container/array.hpp
  • castle/core/types.hpp
  • castle/core/traits.hpp

Public API

APIDescription
observer<T>Abstract observer interface with notify(T const&).
observer<void>Abstract observer interface for parameterless notifications.
observer<T, Rest...>Multiple-inheritance helper that exposes all notify() overloads for unique payload types.
observable<TObserver, N>Stores up to N observer pointers in fixed-capacity inline storage.
add_observerRegisters a non-null observer pointer; rejects duplicates and overflow.
remove_observerUnregisters a previously added observer pointer.
notify_observersInvokes notify(data) or notify() on every registered observer.

Usage example

See samples/patterns/observer.cpp.

#include "castle/patterns/observer.hpp"

struct temperature_observer : castle::patterns::observer<uint16_t>
{
    void notify(uint16_t const& value) override { last = value; }
    uint16_t last = 0U;
};

Constraints & notes

  • No heap allocation; observable stores observer pointers in castle::container::array.
  • Lifetime management is manual: observers must outlive their registrations.
  • Duplicate registrations are rejected.
  • Dispatch uses virtual functions, so this header does not avoid virtual dispatch even though it remains RTTI-free.

Singleton

An explicitly controlled singleton wrapper that constructs one instance in aligned static storage with no heap allocation. Use it when a process-wide object must be created and destroyed deterministically by the caller.

Dependencies

  • castle/core/compiler.hpp, castle/core/error_handler.hpp, castle/core/traits.hpp, castle/core/types.hpp
  • castle/memory/alignment.hpp, castle/memory/new.hpp, castle/utility/utility.hpp

Public API

APIDescription
singleton<T>Static-only wrapper around one T stored in aligned in-class storage.
value_typeAlias for the managed type T.
create(Args&&...)Constructs the singleton in place; asserts if it already exists.
destroy()Destroys the instance; asserts if it does not exist.
instance()Returns a reference to the live object; asserts if not created.
is_valid()Reports whether a live object currently exists.

Usage example

See samples/patterns/singleton.cpp.

#include "castle/patterns/singleton.hpp"

struct service
{
    explicit service(uint32_t seed) : value(seed) {}
    uint32_t value;
};

using global_service = castle::patterns::singleton<service>;

void run()
{
    global_service::create(42U);
    uint32_t const seed = global_service::instance().value;
    global_service::destroy();
}

Constraints & notes

  • No heap allocation; construction uses placement new into aligned static storage.
  • Lifetime is controlled explicitly by create() and destroy().
  • create() and destroy() are not thread-safe; synchronize lifecycle changes externally.
  • Misuse is reported through Castle assertions instead of exceptions.

Visitor

Variadic visitor and visitable base helpers for classic visitor-style dispatch. Use it when concrete node types need a shared visitor interface with compile-time-checked overload sets.

Dependencies

  • castle/core/compiler.hpp
  • castle/core/traits.hpp

Public API

APIDescription
visitor<T1, Types...>Combines multiple visit() overload requirements through recursive inheritance.
visitor<T1>Base case declaring one pure virtual visit(T1).
visitable<T1, Types...>Combines multiple accept() overload requirements through recursive inheritance.
visitable<T1>Base case declaring one pure virtual accept(T1&).

Usage example

See samples/patterns/visitor.cpp.

#include "castle/patterns/visitor.hpp"

struct start_command;
struct stop_command;

struct command_visitor : castle::patterns::visitor<start_command&, stop_command&>
{
    void visit(start_command&) override {}
    void visit(stop_command&) override {}
};

Constraints & notes

  • No heap allocation or RTTI.
  • visit() and accept() are pure virtual, so dispatch is runtime polymorphic rather than CRTP or static.
  • Parameter types must be unique; duplicates are rejected with static_assert.

Chain of responsibility

An ordered list of handlers, where each handler pairs a predicate with an action. A request walks the list until a handler ends the chain. Use it for guarded processing or first-match dispatch without handler base classes or virtual calls.

Dependencies

  • castle/callbacks/function.hpp, castle/container/array.hpp, castle/error/status.hpp
  • castle/utility/tuple.hpp, castle/utility/integral_sequence.hpp, castle/core/traits.hpp, castle/core/types.hpp

Public API

APIDescription
handler_flowAction result: continue_chain (same as a void action) or stop_chain.
reject_policyBehavior on a false predicate: stop (default) or skip.
chain_resultOutcome of process(): completed, stopped, or rejected.
conditional_handler<Predicate, Action, OnReject>Predicate and action stored by value; exposes process(args...).
make_handlerDeduces a handler that ends the chain with rejected when its predicate is false.
make_skippable_handlerDeduces a handler that is skipped when its predicate is false.
make_default_handlerDeduces a handler whose predicate always accepts.
chain_of_responsibility<Handlers...>Static chain: handlers are fixed by type, stored in a tuple, and dispatched with a compile-time fold.
make_chainDeduces a static chain from its handlers.
chain.process(args...)Runs handlers in declaration order and returns chain_result.
chain(args...)Returns handler_flow, so a chain can be nested or connected to a signal slot.
chain.handler_at<I>()Compile-time indexed access to a handler.
bounded_chain_of_responsibility<MaxHandlers, void(Args...)>Runtime-registered chain with fixed capacity; each slot holds a whole handler in a callbacks::function.
add_handler, add_skip_handler, add_default_handlerAppends a handler with the matching reject policy and returns status.
clear()Removes all handlers; returns invalid_config while processing.
size(), empty(), is_processing(), capacity()Bounded chain state queries.

Usage example

See samples/patterns/chain_of_responsibility.cpp.

#include "castle/patterns/chain_of_responsibility.hpp"

namespace dp = castle::patterns;

struct request { unsigned code; };
struct stats { unsigned seen = 0U; unsigned handled = 0U; unsigned ignored = 0U; };

auto chain = dp::make_chain(
    dp::make_default_handler([](request const&, stats& s) noexcept { ++s.seen; }),
    dp::make_skippable_handler(
        [](request const& r, stats&) noexcept { return r.code == 7U; },
        [](request const&, stats& s) noexcept
        {
            ++s.handled;
            return dp::handler_flow::stop_chain;
        }),
    dp::make_default_handler([](request const&, stats& s) noexcept { ++s.ignored; }));

request req{7U};
stats counters;
chain.process(req, counters);   // chain_result::stopped

Constraints & notes

  • No heap allocation, exceptions, RTTI, or virtual functions.
  • A void action continues the chain; return handler_flow::stop_chain to end it.
  • A false predicate ends the chain with rejected unless the handler is skippable.
  • A nested chain reports stop_chain for both stopped and rejected, so a rejection also ends the outer chain.
  • Every handler receives the same lvalue arguments; the bounded chain rejects rvalue-reference parameters.
  • The bounded chain stores each handler in one inline slot, so its predicate and action must fit StorageSize.
  • add_handler() and clear() fail with invalid_config while a process() call is active.
  • No internal synchronization.

Action sequence

A fixed-capacity sequence of one-shot calls and delays that runs in order, modeled on the cocos2d-x Sequence. The owner advances time with update(elapsed), so the sequence never reads a clock and stays deterministic when driven from a main loop or a tick callback.

Dependencies

  • castle/callbacks/function.hpp, castle/container/array.hpp, castle/chrono/duration.hpp, castle/error/status.hpp
  • castle/math/ratio.hpp, castle/utility/forward.hpp, castle/core/traits.hpp, castle/core/types.hpp

Public API

APIDescription
action_sequence_stateidle, running, or completed.
action_sequence<MaxActions, Duration, CallbackStorageSize, CallbackStorageAlignment>Owns up to MaxActions steps. Duration sets the time resolution (default castle::chrono::milliseconds).
add_call(callable)Appends a void() call step. Returns ok, full, invalid_config, or invalid_callback.
add_delay(duration)Appends a delay step. Negative delays return invalid_argument; unrepresentable delays return out_of_range.
append(other)Copies every step of another sequence with the same configuration. full leaves this sequence unchanged.
start()Starts or restarts from the first step. An empty sequence becomes completed.
update(), update(elapsed)Runs every reachable step and returns the state. Leftover time carries past an expired delay.
reset(), clear()Rewinds the run and keeps the steps, or removes every step.
size(), empty(), state(), is_running(), is_completed()State queries.
next_index(), remaining_delay()Progress queries.
capacity()Compile-time MaxActions.

Usage example

See samples/patterns/action_sequence.cpp.

#include "castle/patterns/action_sequence.hpp"

using castle::chrono::milliseconds;
using castle::chrono::seconds;

castle::patterns::action_sequence<4U> sequence;   // millisecond resolution
sequence.add_call([]() noexcept { /* open */ });
sequence.add_delay(milliseconds(1500));
sequence.add_call([]() noexcept { /* close */ });
sequence.start();
sequence.update();                    // runs "open", begins the delay
sequence.update(seconds(1));          // 500 ms left
sequence.update(milliseconds(500));   // delay ends, runs "close", completes

Constraints & notes

  • No heap allocation, exceptions, or RTTI; capacity, time resolution, and callable storage are compile-time parameters.
  • Time finer than Duration does not compile, because truncating it would end delays early.
  • Steps can be added only while the sequence is not running. Calling start(), reset(), clear(), add_*(), or append() from inside a step returns invalid_config.
  • Each update() visits every step at most once, so its cost is bounded by MaxActions.
  • Callables must be copy-constructible and fit CallbackStorageSize.
  • No internal synchronization; drive one sequence from one execution context.

Finite state machine

A compile-time described finite state machine for embedded applications. States and events are C++ types, and a transition table maps an exact (source state, event type) pair to a target state. Optional guard and action functors provide decision and side-effect behavior without virtual dispatch or callback type erasure.

Dependencies

  • castle/core/compiler.hpp
  • castle/core/traits.hpp
  • castle/core/types.hpp

Public API

APIDescription
fsm::empty_contextEmpty context passed to guards and actions by the one-argument process_event() overload.
fsm::always_guardDefault guard; accepts every event.
fsm::no_actionDefault action; does nothing.
fsm::transition<From, Event, To, Guard, Action>Compile-time transition row. Guard defaults to always_guard; Action defaults to no_action.
fsm::event_resultResult enum: transitioned, ignored, or guard_rejected.
fsm::state_machine<Initial, Rows...>FSM type whose states are inferred from the initial state and all transition rows.
state_machine::state_count / transition_countNumber of unique state types and transition rows.
state_machine::state_id<State>()Compile-time state index; rejects state types not present in the machine.
state_machine::current_state_id()Runtime index of the current state.
state_machine::is_in_state<State>()Tests the current state using a state type.
state_machine::has_transition<State, Event>()Compile-time query for a declared state/event pair.
state_machine::process_event(event, context)Processes an event with caller-owned application context.
state_machine::process_event(event)Processes an event with a temporary empty_context.
state_machine::reset()Restores the initial state without running any guard or action.

Usage example

See samples/patterns/fsm.cpp for guards, actions, and multiple source states.

#include "castle/patterns/fsm.hpp"

struct locked {};
struct unlocked {};
struct key_turned {};
struct door_closed {};

using door_fsm = castle::patterns::fsm::state_machine<
    locked,
    castle::patterns::fsm::transition<locked, key_turned, unlocked>,
    castle::patterns::fsm::transition<unlocked, door_closed, locked>
>;

int main()
{
    door_fsm door;
    door.process_event(key_turned{});
    return door.is_in_state<unlocked>() ? 0 : 1;
}

Constraints & notes

  • State types are tags with no runtime state; mutable application data belongs in the context passed to process_event().
  • Event matching is exact on the decayed event type; there is no inheritance-based or runtime-polymorphic matching.
  • Each (source state, event type) pair may appear only once. A false guard returns guard_rejected and does not fall through to another row.
  • Guards and actions must be nothrow default-constructible, noexcept, and callable as functor(context, event).
  • A self-transition runs its guard and action and returns transitioned.
  • reset() only changes the state index. It runs no guards, actions, or hooks.
  • Each instance stores one state index. Dispatch scans the rows in declaration order, so it is O(T) for T rows; state queries and reset are O(1).
  • No internal synchronization. Protect an instance shared across tasks or interrupt contexts.

Decorator

Wraps a callable in outer layers that add behavior, such as tracing, argument checks, result clamping, retry, caching, or guards, without changing how it is called. A decorator is any callable invocable as decorator(next, args...); its body decides what happens before, around, or instead of next(args...). This is the Python decorator model written with templates, with no base class and no virtual calls.

# Python                      // CASTLE
@trace                        auto f = castle::patterns::decorate(target, trace, retry);
@retry                        f(args...);   // trace -> retry -> target
def target(...): ...

Dependencies

  • castle/core/compiler.hpp, castle/core/traits.hpp, castle/utility/forward.hpp
  • Works with, but does not include, castle/callbacks/function.hpp and castle/callbacks/exec_policy.hpp.

Public API

APIDescription
decorated<Target, Decorator>One decorator layer around one target. Both are stored by value.
decorated::operator()(args...)Calls decorator(target, args...), forwarding the arguments unchanged, and returns the result unchanged, references included.
decorated::target(), decorated::decorator()References to the wrapped callable and to the decorator, for example to read a counter.
decorated::target_type, decorator_typeThe stored types.
decorate(target, decorator)Deduces decorated<decay_t<Target>, decay_t<Decorator>>. A function name decays to a function pointer.
decorate(target, d1, ..., dn)Stacks decorators. d1 is the outermost layer and runs first; dn calls the target.

Usage example

See samples/patterns/decorator.cpp.

#include "castle/patterns/decorator.hpp"
#include "castle/callbacks/function.hpp"

namespace dp = castle::patterns;
namespace cb = castle::callbacks;

cb::function<int(int)> square = [](int value) noexcept { return value * value; };

int calls = 0;
auto count_calls = [&calls](auto& next, int value) noexcept
{
    ++calls;
    return next(value);
};

auto limit_to_100 = [](auto& next, int value) noexcept
{
    int const result = next(value);
    return result > 100 ? 100 : result;
};

// count_calls -> limit_to_100 -> square
auto decorated_square = dp::decorate(square, count_calls, limit_to_100);
int const a = decorated_square(3);    // 9
int const b = decorated_square(20);   // 100, calls == 2

Constraints & notes

  • No heap allocation, exceptions, RTTI, virtual functions, or global state. Every layer resolves at compile time and can be inlined.
  • decorated::operator() is non-const, so targets and decorators can keep state such as counters or caches.
  • Copying a decorated object copies the target and the decorators, including their state, so each copy is independent.
  • Size is the sum of the target and decorators. Wrapping a callbacks::function embeds a copy of it; erase the stack into a function sized for the decorated object, or pass castle::move(fn) to avoid the copy.
  • Arguments reach the decorator exactly as the caller passed them. A decorator that calls next several times (retry) must not move from an argument before the last call.
  • Write decorators as lambdas with auto& next or as functors with a templated call operator. A plain function cannot be a decorator because it cannot name the type of next.
  • A wrapped empty callbacks::function asserts when called; test it first with if (next).
  • Not thread-safe by itself. Synchronize decorators that share state.
